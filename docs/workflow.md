# 多 AI 交接和开发工作流程

## 接手前五步
1. 读根目录 AGENTS.md 和 docs/product-requirements.md。
2. 读 docs/architecture.md、docs/status.md、docs/full-parity-plan.md。
3. 查看 main 最新提交、未合并 PR 与 CI；对照代码核实状态。
4. 明确本任务范围及是否触及主站生产数据、用户权限、微信发布。
5. 不重新开发已完成事项，不覆盖其他 AI 的未合并修改。

## 开发交付
- 推荐每个功能一个可审查的分支/PR；紧急低风险修复按用户授权可合并。
- 修改后完成静态校验与可运行测试，说明模拟测试与真实测试的区别。
- 与主站 API 对接时提供契约表、异常状态、安全边界和真实请求证据。
- 每次更新 docs/status.md，并在 PR 写清变化、验证、风险、待办。
- 避免大规模重构或引入新的数据库/框架，除非有明确性能或维护理由。
- 保留旧代码的兼容性，避免破坏主站线上服务。

## 需要 AI 明确报告
- 代码变更文件与提交 SHA / PR。
- 已通过的检查及其环境。
- 尚未执行的真实 API、微信编译、真机、后台审核验证。
- 当前阻碍与最小的用户配合步骤。
- 是否有任何生产写入、外部发布或权限变更。

## 权限与安全
- 用户授权尽快持续推进常规代码开发和可审查合并。
- 账号授权、密钥、公开权限、生产数据库、用户真实信息和微信正式上架不因“尽快”而省略安全审查或平台要求。
- 不要求用户在聊天里发送密钥；使用已配置的安全服务端凭证机制。
- 不在 README/日志/测试固定数据中提交实际个人信息。

## 给下一位 AI 的第一条任务
先读 AGENTS.md、docs/product-requirements.md、docs/architecture.md、docs/status.md；检查当前 GitHub main/PR，再从“真实 API 契约和详情独立加载”开始。必须直接实施小而可验证的改动，不要只给空泛计划。
